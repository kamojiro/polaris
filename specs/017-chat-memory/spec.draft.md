# 017. チャットの長期記憶(テーマ別メモファイル)

## ステータス

未着手

## 概要

チャットの会話から、テーマごとに永続的な知識を抽出・蓄積し、以後の関連する会話で前提知識として使えるようにする。「ローカルLLM」「LLM論文」「mac/Linux環境」のような、繰り返し話すテーマについて、以前の内容を踏まえた応答ができるようにするのが目的。

## 背景・判断

- Cowork(Claude)自身が使っている長期記憶の仕組み(トピックごとに1ファイル、インデックスで一覧管理、内容が増えたら書き換え)と同じ形のパターンを採用する。mem0/Letta等のエージェントメモリ系プロダクトも同様の考え方
- 「不要なことを記録したくない」と「管理は面倒」という一見相反する要望に対し、候補→承認のゲート方式は採用せず、ログ層+現在状態層の二層構造で解決する

## アーキテクチャ: ログ層と現在状態層の分離

一つのファイルに全部載せようとすると「履歴として何が起きたか」と「今の理解はどうなっているか」が両立しない。これはevent sourcing(追記のみのログ)+ materialized view(そこから導出される現在状態)という定番パターンで解決する。

- **ログ層**: `MemoryEvent`テーブル(theme, extracted_at, source_conversation_turn, raw_text)。追記のみ、削除・編集しない
- **現在状態層**: `memory/<theme-slug>.md`(1テーマ1ファイル)。会話に読み込ませる実体はこちら。対象テーマのログをもとにLLMが書き直す(read-modify-write)。`019-diary-domain`も同じ「ログ層+現在状態層、LLMによるread-modify-write」の仕組みをキーが日付の場合として使う想定だが、保存先ディレクトリは`memory/`と`diary/`で分ける(仕組み=コードは共通化しうるが、保存場所はテーマと日付で混在させない)

チャット履歴との違いは3つ。(1) フィルタリング: チャット履歴は雑談も含め全部残るが、ログ層はLLMが「記憶に値する」と判断したものだけ。(2) 再編成: チャット履歴は会話ごとの時系列で全テーマが混ざるが、ログ層はテーマ単位に束ね直される。(3) 独立性: チャット履歴が将来ローリングウィンドウ等で刈り込まれても、ログ層はそれと無関係に永続する。テーマの見直し(「たまに整理」)はログ層だけを読み返せばよく、チャット履歴全体の再スキャンが不要になる。

## 抽出トリガー

ターンごとにバックグラウンドで実行する。既存の`on_complete`フック(`015-paper-qa-chat`で使用量イベント表示のために導入したもの)と同じ仕組みを再利用し、チャット応答自体はブロックしない。`docs/adr/0003-chat-turn-pipeline.md`で定義した3段パイプラインの「後処理」段に位置づける。

セッション終端(24時間更新なし等)での抽出も検討したが、複雑さの割にメリットが薄いため見送る。ターンごとの抽出で十分。

## 抽出フロー

1. 直近のやり取り(最新の1往復、または直近数往復)と既存テーマ一覧(インデックス)をLLMに渡す
2. LLMが判断: (a) 記憶に値する内容が含まれるか、(b) 含まれる場合、既存テーマに該当するか新規テーマか
3. 該当なしと判断されたら何もしない(承認ゲートではなくLLMの判断が「不要なことを記録しない」の防波堤)
4. 該当ありなら`MemoryEvent`に追記し、対象テーマの現在状態ファイルをログをもとに書き直す

## テーマの決め方

デフォルトは自動(オープンセット分類、既存テーマ一覧から選ぶか新規作成)。加えて、ユーザーが明示的に指示すればテーマの見直し(統合・分割・不要テーマの削除等)ができるようにする(例:「ローカルLLMのテーマを整理して」)。

## テーマ再編とログ層の関係

テーマの統合・分割・改名を行うと、ログ層の`MemoryEvent.theme`もそれに追従させる必要がある。ログ層のうち不変(追記のみ、編集しない)なのは`raw_text`(実際に抽出された内容)であって、`theme`(分類ラベル)はテーマ再編時に更新してよい。再分類してもraw_text自体は消えないので「何が起きたか」は失われない。

- 改名・統合: 機械的な一括更新(該当する`theme`の値をまとめて書き換えるだけ)で済む
- 分割: どの旧エントリがどの新テーマに属するかの判断が要るため、対象テーマのログ全体をLLMに渡して再分類させる(抽出時の分類判断と同じ仕組みを再利用できる)

再編後は、影響を受けたテーマの現在状態ファイルを、更新済みのログから作り直す。

## 記憶の想起(会話への注入)

`docs/adr/0003-chat-turn-pipeline.md`で定義した3段パイプラインの「前処理」段として位置づける。メインのチャットエージェントに「テーマ一覧を見て呼ぶか判断させるtool」は持たせない。応答生成モデルに「必要なら能動的にtoolを呼べ」と期待するのは信頼性が低い(agentic systemsでよくある、optionalなtool呼び出しをLLMが単に忘れるという問題)。代わりに、抽出フロー(ターン後)と対称な専用の軽量LLM呼び出しを、ターン前に同期的に挟む。`agent/extract_metadata.py`/`agent/structure_paper.py`と同じ「狭いタスクを小さいモデルに閉じてやらせる」パターンをここでも踏襲する。

1. メインのチャットエージェント呼び出しの前に、直近のユーザー発言(+直前数往復)とテーマインデックス(slug + 一行説明)を、専用の軽量LLM呼び出しに渡す
2. 「該当テーマなし」/「該当テーマあり(どれか1つ、または複数)」を判定させる
3. 該当ありなら、コード側でそのテーマの現在状態ファイルを読み込み、メインのチャットエージェント呼び出しのコンテキスト(system prompt相当)に直接注入する。tool呼び出しの往復は挟まない(判定した時点でファイルは特定できているため)

015の論文モード(AG-UI stateで「今読んでいる論文」を明示的に固定する仕組み)とは前提が違う。論文モードは「(この論文を)開く」という明示的なユーザー操作を起点にできるが、テーマの想起は会話の自然な流れの中で暗黙に発生することが多い。ユーザーが「ローカルLLMの話の続き」のように明示した場合にstateで固定する拡張は、将来必要になれば015のパターンを踏襲して追加する(v1では見送り)。

トレードオフ: 抽出(ターン後)は`on_complete`でバックグラウンド実行のため応答をブロックしないが、想起(ターン前)はメイン応答生成の前に完了している必要があるため同期呼び出しになり、軽量モデル1回分のレイテンシが毎ターン乗る。開発フェーズ(無料枠モデル)なら実質許容範囲と見ているが、本番フェーズでの実測は未決定事項に記載。
