# 019. 日記ドメイン

## ステータス

💤 スケルトンのみ

## 概要

チャットで会話することで日記がつけられる機能。日付ごとに1つのエントリを持ち、会話の内容からLLMが日記本文を組み立てる。チャット入力欄に「日記モード」のような選択肢を設け、明示的にモードへ入ってから会話する運用を想定(2026-08-23、雑談から着想)。

## 背景・判断

- `017-chat-memory`と同じ「ログ層+現在状態層(LLMによるread-modify-write)」の仕組みを、グルーピングキーを「テーマ」ではなく「日付」に変えて再利用できそうという着想。ただし017とは性質が2点異なる。
  1. 017は「記憶に値するか」をLLMに判断させて選別するが、日記モードでは(モードに入っている間の)会話内容は基本的に全部記録対象になる。選別ステップの意味合いが違う
  2. 017はテーマへの自動分類(オープンセット分類)が要るが、日記のキーは「今日の日付」で自明に決まるため、分類ステップ自体が不要
- チャット入力欄の「日記モード」トグルは、`015-paper-qa-chat`のPaperModeState(AG-UI stateで「今読んでいる論文」を明示的に固定する仕組み)と同じ構造(「入る」という明示的なユーザー操作を起点にできる)。実装パターンをそのまま踏襲できそう
- 現在状態ファイルの保存先は`memory/<theme-slug>.md`とは別ディレクトリの`diary/<entry_date>.md`にする。ログ層+現在状態層という仕組み(コード)は017と共通化しうるが、保存場所はテーマと日付でディレクトリレベルで分ける(2026-08-23、明示的に要望あり)

## データモデル(たたき台)

Hub/Satelliteパターンを踏襲する。

```python
class DiaryRecord(SQLModel, table=True):
    __tablename__ = "diary_records"

    id: str = Field(primary_key=True)
    item_id: str = Field(foreign_key="items.id", index=True)
    entry_date: date = Field(index=True, unique=True)  # 1日1エントリ
    content: str        # 日記本文。会話からLLMが都度read-modify-writeする
    updated_at: datetime
```

`ItemType`に`diary = "diary"`を追加する。

## 未決定事項

- 日記モード中の会話をターンごとに書き直すか、モード終了時にまとめて1回書くか(017の「書き直し頻度」の未決定事項と同じ論点)
- 日記モードじゃない普通の会話からも日記に値する内容を拾うか、完全にモード限定にするか(017のような「常時バックグラウンド抽出」寄りにするか、明示モード限定に寄せるかは検討要)
- 過去の日記をチャットで想起できるようにするか(`013`/`015`と同じ「全文をコンテキストに渡す」方式が使えそう。例:「先週の水曜どうだったっけ」)
- チャット入力欄の「モード」概念を、015のPaperModeStateと今回のDiaryModeStateとで共通化するか、個別に持つか。現時点では2例のみなので、3例目が出てから一般化を検討する(rule of three、`011-agent-registry`のYAGNI判断と同じ考え方)
- 一覧・振り返りUI(`009-dashboard`待ちか、チャット経由の閲覧で十分か)
