## 概要

チャットで会話することで日記がつけられる機能。日付ごとに1つのエントリを持ち、会話の内容からLLMが日記本文を組み立てる。チャット入力欄に「日記モード」のような選択肢を設け、明示的にモードへ入ってから会話する運用を想定(2026-08-23、雑談から着想)。

## 背景・判断

- `017-chat-memory`と同じ「ログ層+現在状態層(LLMによるread-modify-write)」の仕組みを、グルーピングキーを「テーマ」ではなく「日付」に変えて再利用できそうという着想。ただし017とは性質が2点異なる。
  1. 017は「記憶に値するか」をLLMに判断させて選別するが、日記モードでは(モードに入っている間の)会話内容は基本的に全部記録対象になる。選別ステップの意味合いが違う
  2. 017はテーマへの自動分類(オープンセット分類)が要るが、日記のキーは「今日の日付」で自明に決まるため、分類ステップ自体が不要
- チャット入力欄の「日記モード」トグルは、`015-paper-qa-chat`のPaperModeState(AG-UI stateで「今読んでいる論文」を明示的に固定する仕組み)と同じ構造(「入る」という明示的なユーザー操作を起点にできる)。実装パターンをそのまま踏襲できそう
- 現在状態ファイルの保存先は`memory/<theme-slug>.md`とは別ディレクトリの`diary/`にする。ログ層+現在状態層という仕組み(コード)は017と共通化しうるが、保存場所はテーマと日付でディレクトリレベルで分ける(2026-08-23、明示的に要望あり)。ファイル単位(月ごとか日ごとか)は下記「保存形式」参照(2026-08-29改訂)

## UI設計: チャット入力欄まわり(2026-08-23、モックアップで確認済み)

paper/IRモードのような**エンティティ紐付き型**と、日記モードのような**姿勢型**は仕組みが違うため、stateは単一の「今のモードenum」にまとめず、独立したフィールドとして持たせる。両者は排他ではなく共存を許す(論文について話しながら、その内容を今日の日記にも残す、という使い方を想定)。

```python
class ChatUIState(BaseModel):
    paper_mode: PaperModeState | None = None
    diary_mode: bool = False
    # 将来: ir_mode: IrModeState | None = None
```

見た目(フロントエンド)は以下で統一する。

- 入力欄の上に「モードチップ」を横並びで表示する。paper/IRモードのチップはタイトル付き(例: 「📄 Attention Is All You Need」)で一覧クリックにより出現、日記モードのチップはラベルのみ(「📔 日記モード」)。どちらもチップ右の`×`で退出できる
- 日記モードは対応する一覧が存在しないため、入力欄のツールバーに専用のトグルボタン(ノートアイコン)を置き、そこがトグルの起点になる。押すたびにチップの出現/消滅が連動する
- 日記モードの持続性は、paperモードと同じく**セッション単位**(ONにしたらOFFにするまで続く)にする。送信のたびにリセットされる単発トグルにはしない

## データモデル(たたき台)

Hub/Satelliteパターンを踏襲する。

```python
class DiaryRecord(SQLModel, table=True):
    __tablename__ = "diary_records"

    id: str = Field(primary_key=True)
    item_id: str = Field(foreign_key="items.id", index=True)
    entry_date: date = Field(index=True, unique=True)  # 1日1エントリ
    content: str        # 日記本文。会話からLLMが都度read-modify-writeする
    updated_at: datetime
```

`ItemType`に`diary = "diary"`を追加する。

## v1後の検討メモ(2026-08-30、同日中に実装完了)

`research.md`の「将来のための伏線」を補足する形で、v1完了後に着想したもの。着想メモとして
書いた同じ2026-08-30のうちに、正式なUser Story 4-6として`/speckit-specify`〜`/speckit-implement`の
フローに乗せて実装まで完了させた。以下は着想時点のメモとして原文のまま残す(実際の設計判断は
`research.md`、実装状況は`spec.md`参照)。

- **過去の日記をチャットで想起できるようにするか**: 日付が特定できる質問(「先週の水曜どうだった」)は検索不要で、`DiaryRecord.entry_date`から直接引けばよい。日付が分からずテーマで探したい質問(「プロジェクトの調子が良かった頃っていつだっけ」)は候補日の絞り込みが要る。まずは`DiaryRecord.content`に対する素朴な`LIKE`検索で様子を見て、精度不足が実際に問題になってからSQLite FTS5(`ADR-0001`で採用方針のみ決定・実コードでは未使用)への移行を検討する。FTS5は外部コンテントテーブル方式だと元テーブルとの同期(INSERT/UPDATE/DELETEをトリガーで反映)を自前で保守する必要があり、日記程度のデータ量(1日1件)では`LIKE`で十分な可能性が高いため、後回しにする判断
- **バックフィル書き込み(2026-08-30追記)**: 日記は溜めがち(その日のうちに書かない)な運用が実際に想定されるため、「過去日を指定して書く」は仮説的なエッジケースではなく現実の需要として記録しておく。書き込みtoolに`target_date`引数を足し、LLMが文面(「先週の水曜」「8/25の日記に追記して」等)から対象日を推定して渡す想定。日付解釈の精度に依存するため、実装時期・v1後のどのタイミングで着手するかは未定のまま
- **具体的なuser story(2026-08-30追記)**: 「この日の日記を見たい」「8月の日記を要約して」の2つは具体的な需要として想定しておく。当初「日付指定」「月指定」を別toolにする案(`get_diary_by_date`/`get_diary_month`)を検討したが、`start_date`/`end_date`を取る単一tool`get_diary_range`に統合した(1日だけ見たい場合は`start_date == end_date`で呼べる)。読み取り元は`diary/daily_YYYYMM.md`ファイルではなく**`DiaryRecord`テーブルへの`entry_date BETWEEN`範囲クエリ**にする。月をまたぐ範囲(7月末〜8月頭等)でも複数ファイルを読んでスライスする必要がなく、日次DBの範囲クエリだけで完結するため。

  ```python
  class DiaryDayResult(BaseModel):
      entry_date: date
      content: str

  class DiaryRangeResult(BaseModel):
      entries: list[DiaryDayResult]  # 実在する日だけ、無い日は含めない

  def get_diary_range(start_date: date, end_date: date) -> DiaryRangeResult:
      if (end_date - start_date).days > 62:
          ...  # LLMに範囲を絞るよう伝えて弾く
  ```

  期間の上限は62日に決定(それ以上は想定しにくいが、`get_paper_full_text`と同種の「全文コンテキスト」toolなので、広すぎる範囲によるコンテキスト膨張を防ぐガードとして最低限入れておく)。`get_diary_range`は`docs/adr/0012-trim-stale-tool-results-from-history.md`の`FULL_TEXT_TOOL_NAMES`に登録し、同じ蓄積問題を再発させないこと。書き込み系(日次read-modify-write)のtoolとは別物で、そちらへの変更はない
- **日記モードの会話も`017-chat-memory`の記憶抽出(後処理)の対象にする**: 現状の`_extract_memory_task`はモードを問わず全ターンで無条件に呼ばれる実装になっているため、日記モード実装時にこれを意図せず止めないよう注意する。「記憶に値するか」の選別は017の既存の軽量分類器にそのまま任せられるため、日記の内容がテーマ別の記憶(`memory/<theme-slug>.md`)にも反映されるのは追加実装なしに実現できる見込み

## UI設計: 執筆中の日記を表示するパネル(2026-08-30、モックアップで確認済み)

日記モード中、書いている内容がその場で見えないと不安、という声から着想。

- **表示トリガー**: `diary_mode`をONにした瞬間ではなく、**日記モード中に最初のメッセージを送信した後**にパネルを表示する。モードに入っただけの時点では当日分がまだ存在せず、空の「本日」枠を見せることになって座りが悪いため。既存の「ターン完了後に再取得」の仕組みにそのまま乗る形になり(初回送信=最初のターン完了=最初の取得)、モード切替時専用の初期フェッチを別に用意する必要もない。日記モードを抜けたら非表示に戻す
- **表示内容**: 直近3日分(2日前・前日・当日)を、日付の古い順に上から下へ並べる。一番下が当日=書いている最中のエントリで、視覚的に強調する(アクセント色の左ボーダー+「本日」ラベル)。古い日ほど薄く表示し、当日との対比を出す
- **データ取得元**: `daily_YYYYMM.md`(LLM編集用のmarkdown)ではなく**`DiaryRecord`テーブルを`entry_date` DESCで直接クエリ**する。月境界(月初に「2日前」が前月ファイルにまたがるケース)をmarkdown再パースで扱うより、DBの日付インデックスを素直に使う方が単純。新規に軽量なエンドポイント(例: `GET /api/diary/recent?count=3`)が要る
- **更新タイミング**: 当日分は017/paper-qaの使用量表示等と同じパターンで、**ターン完了後にパネルのデータを再取得**する(read-modify-writeで内容が変わるため)
- **折りたたみ**: パネルヘッダーに開閉トグルを置き、日記モードを維持したまま一時的にパネルを隠せるようにする(モードチップの`×`退出とは別の操作)
- **狭い画面での扱い**: 常時サイドバーだと圧迫する幅では、開閉式ドロワーに切り替える(閾値・具体実装は未定)
- **強調する行(アンカー)の決め方**: 「今日」固定ではなく、**`DiaryRecord.updated_at`が最も新しい行**をアンカーとする。バックフィル(過去日を後から書く、下記参照)を許すと「今まさに書いているのは今日とは限らない」ため、チャット側からフロントに「今どの日付を編集中か」を明示的に伝える仕組み(AG-UI stateへの追加等)は用意しない。`GET /api/diary/recent`は`updated_at` DESCで1件アンカーを取り、そこから`entry_date < アンカー`を`entry_date` DESC LIMIT 2で前後の文脈として足す(バックフィルで飛び石の日付があっても、直前に存在する日を素直に拾えるため、`アンカー日-1日`のような日付計算はしない)。この方式ならターン完了後に同じエンドポイントを叩き直すだけで済み、「いつ書いたか」情報をチャット経路で別途フロントに渡す必要がなくなる

## 気になっていること: 日記モードでサイドバーが広がるのをやめたい(2026-09-14)

日記モードに入ると執筆中パネル(上記)がサイドバーとして表示され、レイアウト幅が広がる挙動になっているが、これをやめたい。paper/IRモードのような**エンティティ紐付き型**は専用パネルを持たず、モードチップの表示だけでレイアウト幅に影響しない(会話の文脈として論文/IR文書を保持するだけ)。日記モードも同じように、レイアウトを恒常的に広げない見せ方に変えられないか、という提案。

- **候補1: paper/IRモードに寄せる**: 専用パネル自体をやめ、必要なら「直近の日記を見せて」のようにチャットで能動的に聞く形にする(`get_diary_range`は既にある)。ただしこれは「書いている内容がその場で見えないと不安」という当初の着想を後退させることになる
- **候補2: canvas的なオーバーレイにする**: レイアウトを横に押し広げる常設サイドバーではなく、必要な時だけ画面上に重なって出るオーバーレイパネル(ChatGPTのCanvasやClaudeのArtifactに近い見せ方)にする。開閉してもチャット本体の幅は変わらない。既存の「狭い画面ではドロワーに切り替える」という設計を、画面幅を問わず常にドロワー/オーバーレイにする形に寄せるとも言える
- Polaris内にcanvas/artifact的な汎用UIコンポーネントは今のところ存在しない(調査要)。もし今後他の用途(例: 027の統合結果表示、026の何か)でも「一時的に大きめのコンテンツを見せたい」需要が出るなら、日記専用パネルではなく汎用のオーバーレイコンポーネントとして`003-chat-ui-polish`側で設計した方が筋が良いかもしれない
- **方針決定(2026-09-15)**: 画面全体での配置は「サイドバーを一時的に隠し、画面を左右半分に分割してチャットと日記を同格で並べる」canvas的な方式に決定。既存の`Sidebar.tsx`(pickup/discord/論文調査)は日記モード中は非表示にし、その領域を日記パネル(画面幅の約半分)に置き換える。日記モードを抜けたら通常のサイドバー表示に戻す。他の候補(専用カラム追加/オーバーレイ浮遊/サイドバー内区画/中央ポップアップ)は不採用。中央ポップアップは入力欄が隠れて「見ながら会話を続ける」用途に合わないため特に不採用
- この「サイドバーを隠してcanvas的に半々分割」というパターンは日記専用にせず、汎用のレイアウトモードとして実装するのが良さそう(`027-related-paper-research`の統合結果表示でも同じパターンを採用することが決まったため、`003-chat-ui-polish`側で共通コンポーネント化を検討する)
- **実装用モックアップ**: `specs/019-diary-domain/layout-mockup.html`(このリポジトリ内)に実物HTML/CSSを置いた。実装時はこのファイルを直接参照すること(`003-chat-ui-polish`の`composer-mockup.html`と同じ運用、文章の説明だけに頼ると意図と異なる見た目になった前例があるため)

### 追記: パネル内の見づらさ(2026-09-14、実機スクリーンショットで確認)

サイドバー幅を広げる/広げないの問題とは別に、今の中身の見せ方自体が見づらい。実機では3日分の本文(段落)が、日付見出しだけを挟んで縦にそのまま積まれており、狭い列幅で長めの段落が詰まって見える。当日分は左ボーダー+「編集中」バッジで区別されているが、それ以外は視覚的な区切りが弱い。

- 改善候補: 当日以外(2日前・前日)は全文ではなく1〜2行程度のプレビュー(先頭だけ、または省略記号)に縮め、当日分だけをフル表示にして視線の焦点を絞る
- 改善候補: 日付ブロックごとにカード的な区切り(背景色・余白・薄い罫線)を入れ、テキストが地続きに見えないようにする
- 上記の「サイドバーが広がるのをやめたい」の対応(オーバーレイ化等)で列幅自体が広がれば、この見づらさもある程度軽減される可能性があるため、両方セットで見直すのが良さそう
