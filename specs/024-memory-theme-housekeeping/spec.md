# Feature Specification: 記憶テーマの定期棚卸し(memory-theme-housekeeping)

**Feature Branch**: `024-memory-theme-housekeeping`

**Created**: 2026-09-01

**Status**: ✔️ 完了(2026-09-02)。`plan.md`/`research.md`/`data-model.md`/`contracts/`/`quickstart.md`/`tasks.md`まで完了し、実装済み。手動E2E(`quickstart.md`シナリオ1〜5)は使い捨てのscratch DB+別ポートのバックエンド/フロントで検証し、実LLM呼び出しによる統合・stale検出、通知バナー表示、既読管理(閉じる→再表示されない→新バッチ後は再表示)を確認した

**Input**: User description: "017-chat-memoryの記憶テーマを定期的に棚卸しし、統合・分割・stale候補を「提案」として検出・表示する機能。v1スコープは検出・表示のみ(提案の実適用は含めない、017に再編ツール自体が無いため)。023-daily-summary-notificationと同じcron駆動・完全読み取り専用パターンを踏襲する。書き込み用API・per-suggestionの既読管理は持たず、検出結果は毎回のバッチ実行で最新1件に全置き換えする。既読管理は023と同じくフロントのlocalStorageで『最後に見たgenerated_at』を比較する方式。通知UIは`DailySummaryBanner.tsx`とほぼ同型(specs/024-memory-theme-housekeeping/spec.draft.md、2026-08-26起票、2026-09-01に方針確定)。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 記憶テーマの整理候補が自動的に検出される (Priority: P1)

017-chat-memoryで蓄積された記憶テーマ(`memory/<slug>.md`)は、テーマ数が増えるにつれて内容が重複したり、1テーマに複数の話題が混在したり、長期間更新されないまま古くなったりする。ユーザーが手動で気づいて整理を頼まなくても、定期的なバッチ処理が全テーマの現在の内容を読み、統合(似た内容の複数テーマ)・分割(1テーマに複数話題が混在)・stale(長期未更新)の候補を自動的に検出する。

**Why this priority**: これが無ければ機能自体が存在しない。他のユーザーストーリーはこの検出結果の上に成り立つ。

**Independent Test**: 内容が重複する2つの記憶テーマファイルを用意した状態でバッチ処理を実行し、統合候補として検出されることを、保存された検出結果を直接確認することで単独で検証できる(通知UIが無くても検証可能)。

**Acceptance Scenarios**:

1. **Given** 内容が明らかに重複する2つの記憶テーマが存在する、**When** バッチ処理が実行される、**Then** その2テーマを対象とした統合候補が、具体的な理由の説明とともに検出・保存される
2. **Given** 記憶テーマが1件以下しか存在しない、**When** バッチ処理が実行される、**Then** エラーにならず、検出候補0件のまま正常に完了する
3. **Given** 前回のバッチ実行で検出された候補が存在する、**When** 新しいバッチ処理が実行される、**Then** 前回の候補は新しい検出結果で完全に置き換えられる(蓄積されない)

---

### User Story 2 - 整理候補があることにチャット画面で気づける (Priority: P2)

ユーザーは記憶テーマの整理候補を能動的に確認しに行かなくても、普段どおりチャット画面を開くだけで「整理の提案があること」に気づける。

**Why this priority**: P1で検出できても、ユーザーがその存在に気づく手段が無ければ実用上は使われない機能になる。P1の直後に価値を持つ。

**Independent Test**: 検出済みの候補がある状態でチャット画面を開き、通知(バナー)が表示され、候補の件数と各候補の具体的な内容が読めることを目視確認できる。

**Acceptance Scenarios**:

1. **Given** 最新のバッチ実行で1件以上の候補が検出されている、**When** ユーザーがチャット画面を開く、**Then** 候補の件数と、各候補の対象テーマ・種別・理由が読める通知が表示される
2. **Given** 最新のバッチ実行で候補が0件だった、**When** ユーザーがチャット画面を開く、**Then** 通知は表示されない

---

### User Story 3 - 一度確認した提案は繰り返し通知されない (Priority: P3)

ユーザーが一度提案の内容を確認したら、同じ内容の提案が毎回のチャット画面表示のたびに繰り返し通知されて邪魔になることはない。ただし、提案自体が消えるわけではなく、新しい検出結果が出るまでは(明示的に開けば)引き続き確認できる。

**Why this priority**: P1・P2が正しく動いていても、これが無いと同じ提案が延々と通知され続け、通知疲れでユーザーが無視するようになってしまう。機能の正しさそのものより一段低い優先度だが、実用上は早期に必要。

**Independent Test**: 通知を閉じた後にチャット画面を再読み込みし、同じバッチの通知が再表示されないことを確認できる。別のバッチ実行後(新しい検出結果が出た後)は再び通知されることも確認できる。

**Acceptance Scenarios**:

1. **Given** 通知が表示されている、**When** ユーザーが通知を閉じる、**Then** 画面を再読み込みしても同じ内容の通知は再表示されない
2. **Given** ユーザーが前回の通知を閉じた、**When** 新しいバッチ実行で(前回と異なる)検出結果が保存される、**Then** 新しい内容の通知が表示される

---

### Edge Cases

- 記憶テーマが0件の状態でバッチ処理が実行されたら? → 検出候補0件として正常終了する(エラーにしない)
- 直前のバッチで候補が3件あったが、今回のバッチで0件になったら? → 直前の3件は破棄され、通知は表示されなくなる(「最新の状態を常に反映する」という設計のため、履歴として残さない)
- 同じ内容の候補が複数回連続のバッチで検出され続けたら? → 通知としては`generated_at`が変わるたびに再表示されうる(そのバッチが前回と同一内容でも、ユーザー側で一度閉じていなければ通知される)。同一内容の再通知を抑制する仕組みはv1の範囲外とする
- バッチ処理の実行中にチャットの通常利用があったら? → バッチ処理はチャットの応答フローとは独立したバックグラウンド処理のため、チャットの利用に影響しない

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、017-chat-memoryで管理される全ての記憶テーマの現在の内容を読み取れなければならない
- **FR-002**: システムは、読み取った内容をもとに、統合(似た内容の複数テーマ)・分割(1テーマに複数話題が混在)・stale(長期未更新)の3種類の整理候補を検出できなければならない
- **FR-003**: 各整理候補は、種別・対象テーマ・具体的な理由の説明を含まなければならない
- **FR-004**: 検出処理はチャットのターンとは独立したバッチ処理として実行され、チャットの応答生成をブロックしてはならない
- **FR-005**: バッチ処理が実行されるたびに、保存済みの整理候補は今回の検出結果で完全に置き換えられなければならない(過去の検出結果を履歴として蓄積しない)
- **FR-006**: 検出候補が0件の場合、システムはその旨(候補なし)を保存し、既存の候補があれば消去しなければならない
- **FR-007**: ユーザーは、直近のバッチ実行で検出された整理候補の件数と内容を、チャット画面で確認できなければならない
- **FR-008**: 直近のバッチ実行で候補が0件の場合、システムは通知を表示してはならない
- **FR-009**: ユーザーが通知を確認済みとして閉じたら、同じ検出結果に対する通知は再表示されてはならない
- **FR-010**: 新しいバッチ実行によって検出結果が更新されたら、ユーザーが前回の通知を閉じていたとしても、新しい通知が表示されなければならない
- **FR-011**: 本機能は、検出した整理候補(統合・分割・改名)を自動的に適用してはならない。適用手段の提供自体もv1の範囲外とする

### Key Entities

- **記憶整理提案(Memory Housekeeping Suggestion)**: 1回のバッチ実行で検出された、統合/分割/stale候補の1件。種別、対象となる記憶テーマ、検出理由の具体的な説明、検出日時を持つ。バッチ実行のたびに前回分から完全に置き換えられる

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 内容が重複する記憶テーマが存在する状態でバッチ処理を実行すると、統合候補として検出される
- **SC-002**: 整理候補が存在する場合、ユーザーは追加の操作をせずチャット画面を開くだけでその存在に気づける
- **SC-003**: 一度確認した検出結果は、内容が変わらない限り繰り返し通知されない
- **SC-004**: 記憶テーマが0〜1件のような小規模な状態でも、バッチ処理はエラーなく完了する
- **SC-005**: バッチ処理の実行時間が、通常のチャット利用の応答速度に影響を与えない

## Assumptions

- バッチ処理の起動方式は`023-daily-summary-notification`/`008-daily-digest-domain`と同じ「OS cronから独立したバッチ処理を定期的に叩く」想定とする。実際のcron登録(crontab等への登録作業)自体は本specの範囲外の運用作業であり、023/008も同様に未設定のまま手動実行で運用されている現状を踏襲する
- 想定実行頻度は**週1回**とする(023の日次とは異なる)。記憶テーマの重複・分割・stale化は数日〜数週間かけて緩やかに進行するものであり、023のような「その日の活動」と違って毎日の再計算に価値が薄い。また、同一内容の提案でも`generated_at`が変わるたびに再通知されうる(Edge Cases参照)ため、実行頻度を上げるほど通知疲れのリスクが増す。本機能は毎回「全テーマの現在の内容」を読み直す設計(023のような対象期間の絞り込みが無い)ため、頻度はcrontab側の設定のみで表現でき、コード側に頻度用の設定値は不要(023のcrontabコメントと同じ運用パターン)
- 検出精度(何をもって「似ている」「stale」と判断するか)はLLMの判断に委ねる。埋め込みベクトルによる類似度計算のような専用の仕組みは設けない(記憶テーマの母数が現状少なく、投資対効果が薄いため)
- 「通知の既読管理」はブラウザのlocalStorageで行い、023と同じくデバイスをまたいでは同期しない(別デバイスでは再度通知されうる)
- 提案を実際に適用する手段(記憶テーマの統合・分割・改名の実行)は017側に現状存在せず、本specでも新設しない。ユーザーが必要と判断した場合は記憶テーマファイルを直接手動編集する運用に委ねる。将来、実適用の自動化が必要になった場合は別specとして検討する
- 検出候補の種別は「統合」「分割」「stale」の3種類に固定する(spec.draft.mdのたたき台を踏襲)。将来的に他の種別が必要になった場合は別途拡張する
