## 概要

`017-chat-memory`の「たまに整理」は現状ユーザーの明示的な指示(「ローカルLLMのテーマを整理して」)が起点。これを、`023-daily-summary-notification`と同じ`cron`駆動のバックグラウンドタスクとして定期的に自動実行し、整理の「提案」を作っておく(自動適用はしない)。2026-08-26、雑談から着想。

「1日中勝手に調べたり考えたりしてほしい」という要望への最初の具体化の1つ。`023`(日次サマリー)に続く、2つ目のcron駆動タスク。

## 背景・判断

- 017の設計判断(テーマ再編は明示指示が起点)は変えない。本specが作るのはあくまで**提案**であって、統合・分割・改名を自動実行することはしない
- `023`と同じトリガー方式(固定時刻cron)・同じ通知UI(バナー)を再利用する。023の「1日1回サマリー生成」から「1日中いろいろ調べるタスクランナー」への一般化の最初の追加インスタンスとして位置づける
- 3つ目の同種タスク(`025-ir-tracking-expansion`)も同時に着想されており、cron駆動の自律バックグラウンドタスクが3つ目に達する。共通の「タスクランナー基盤」を切り出すべきかは、実際に3つとも動かしてみてから判断する(rule of three、`011-agent-registry`と同じ判断軸)

## やること(v1)

1. 全テーマの現在状態ファイル(`memory/<slug>.md`)とログ(`MemoryEvent`)を読み、以下を検出する
   - テーマ間の重複・統合候補(内容が近い複数テーマ)
   - 分割候補(1テーマに複数の話題が混在している)
   - 長期間更新されていない、実質的に使われなくなったテーマ
2. 検出結果を「提案」としてどこかに保存する(データモデル、下記参照)。この時点では`MemoryEvent.theme`もファイルも一切書き換えない
3. `023`の通知バナーと同じ仕組みで「メモリ整理の提案があります」と表示する。ユーザーが気になったらチャットで「提案を見せて」「その提案通りに整理して」のように話しかけて、既存の017の再編フロー(明示指示起点)を起動する

## 「今の状況調査」「再現性テスト」について(着想メモ、v1では範囲外)

雑談の中で、単なる整理提案に留まらず、テーマの中身が今も正しいか(例: 特定のツール・ライブラリのバージョンが古くなっていないか、Web検索で最新状況を確認する)を能動的に調べたり、記録されている技術的な主張(例:「〇〇は動かない」)を再テストして裏取りする、というアイデアも出た。

これはテーマごとに「何を調べれば裏取りになるか」「何を実行すれば再現テストになるか」がテーマの内容次第でまちまちであり、汎用的な仕組みにしづらい(論文ドメインの`get_paper_full_text`のような、ドメイン固有ツールが必要になりがち)。v1のスコープには含めず、着想として記録するに留める。将来的にやるなら、まず`018-web-search-tool`を使った「このテーマ、最近の情報で古くなってないか軽くチェックする」程度の弱い検証から始めるのが現実的そう。

## データモデル(たたき台)

```python
class MemoryHousekeepingSuggestion(SQLModel, table=True):
    __tablename__ = "memory_housekeeping_suggestions"

    id: str = Field(primary_key=True)
    suggestion_type: str    # "merge" | "split" | "stale" 等
    target_themes: str      # 対象テーマのslugをカンマ区切り等で保持(シンプルな実装優先)
    detail: str             # 提案の具体的な説明(LLMが生成)
    created_at: datetime
    dismissed: bool = False  # ユーザーが「見た」提案を再表示しないためのフラグ
```
