# 0001. ストレージにSQLiteを採用する

## ステータス

採択

## コンテキスト

知識基盤(Item/Chunk/Embedding/Relation/Event)を永続化するストレージを決める必要があった。現時点では個人利用・単一デバイス(実装機であるサーバー1台)が前提で、複数デバイス間の同時書き込みやマルチユーザー対応は要件にない。検索はキーワード検索(著者・タイトル・abstract)とベクトル検索(Chunk embedding)のハイブリッドが必要([[wishlist-design.md]] 3-1、`specs/001-walking-skeleton`)。運用コスト(サーバープロセスの管理・バックアップ)は個人開発として極力抑えたい。

## 決定

ストレージにSQLiteを採用する。全文検索は`FTS5`、ベクトル検索は`sqlite-vec`拡張を使う。

## 検討した代替案

- PostgreSQL + pgvector: 複数デバイス同期やマルチユーザーが要件になった場合により適するが、現時点ではサーバープロセスの運用コストに見合わない。
- 専用ベクトルDB(LanceDB、Chroma等): キーワード検索と別のDBを運用することになり、個人開発で管理対象を増やしたくない。SQLite一本(FTS5+sqlite-vec)でキーワード・ベクトルの両方を賄える方を優先した。

## 結果(Consequences)

良い面: セットアップが単純でファイル1つのため、バックアップ・移動が容易。追加のサーバープロセスが不要で運用コストが低い。

悪い面: 複数デバイス間の同時書き込み・同期が必要になった場合は移行が必要になる。SQLiteは単一ライターロックの制約があるため、書き込みの並行性が要求される規模になったら再検討が要る(個人用途の書き込み頻度では通常問題にならない想定)。
