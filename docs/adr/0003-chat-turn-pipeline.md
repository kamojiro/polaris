# 0003. チャットターンを前処理/メイン/後処理の3段パイプラインとして構成する

## ステータス

採択

## コンテキスト

`015-paper-qa-chat`で`AGUIAdapter.dispatch_request(..., on_complete=...)`を導入し、ターン後の処理(usage/costイベント表示)をメインの応答生成から切り離した。`017-chat-memory`ではさらに、ターン前に「関連テーマの想起(軽量LLM分類→現在状態ファイルの注入)」という前処理が必要になり、ターン後には「記憶抽出」という別の後処理も加わる。

各specがAPI層(`api/app.py`の`/api/chat`)にそれぞれ個別にアドホックな前後処理を書き足していくと、015単体では問題なかったものが、017で前処理が加わり、今後013(IR文書モード)や他ドメインでも同様の需要が出てくるにつれてエンドポイントに処理が分散・混在し、どの処理がどのspecに属するか追いにくくなる。

## 決定

`/api/chat`のリクエスト処理を、以下の3段パイプラインとして構造化する。

1. **前処理**: メインのチャットエージェント呼び出しの前に完了している必要がある処理。結果をsystem prompt/depsに注入する用途(例: 017のテーマ想起)。同期実行必須
2. **メイン処理**: 既存の`build_chat_agent` + `AGUIAdapter.dispatch_request`によるチャット応答生成。ここは変更しない
3. **後処理**: 応答確定後に実行する処理。`on_complete`フックと同じく非同期・バックグラウンドで実行可能(応答をブロックしない)。例: 015のusage/costイベント、017の記憶抽出

前処理・後処理はそれぞれ独立した関数の集まりとして登録し、featureごとに「前処理を使うか」「後処理を使うか」を選べる(全specが両方使う必要はない)。前処理同士が複数存在する場合は`asyncio.gather`等で並列実行し、レイテンシの積み上がりを避ける。

## 検討した代替案

- 現状維持(各specがAPI層にアドホックにフックを足す): 015単体では問題なかったが、017で前処理が加わることで「後処理だけの仕組み」では収まらなくなった。今後specが増えるほど収拾がつかなくなることが見えている
- LangGraph等の汎用オーケストレーション/グラフ実行フレームワークの導入: pydantic-ai + AGUIAdapterで完結している現状規模(3段程度)に対しては過剰(YAGNI)。自前の薄い関数合成で十分

## 結果(Consequences)

良い面: 各specの前後処理が「どの段に属するか」が明確になり、追加・削除・入れ替えがしやすくなる。前処理の並列化、後処理のバッチ化・遅延実行(例: 記憶抽出やテーマ再編を毎ターンではなく間引く)も、該当する段の内部実装を差し替えるだけで対応できる。

悪い面: 前処理段は性質上ブロッキングになるため、複数specが前処理を持つようになると(現状は017のテーマ想起のみだが、将来013のIR文書モード判定なども前処理化されうる)、並列化を徹底しないとレイテンシが積み上がる。段の責務分担が増えるほど、`api/app.py`側の登録・配線コードそのものは多少複雑になる。

## 関連

- 関連spec: `specs/017-chat-memory`(前処理: テーマ想起、後処理: 記憶抽出)
- 関連spec: `specs/015-paper-qa-chat`(後処理パターンの初出、`on_complete`導入元)
- 関連spec: `specs/011-agent-registry`(各段の呼び出し先が将来サブエージェントに置き換わりうる)
