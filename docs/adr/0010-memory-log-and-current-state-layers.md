# 0010. 長期記憶をログ層+現在状態層の二層構造で管理する

## ステータス

採択

## コンテキスト

`017-chat-memory`で、チャットからテーマ別の長期記憶を蓄積したい。「不要なことを記録したくない」(フィルタリング要件)と「管理は面倒」(自動化要件)という一見相反する要望があり、候補→人間承認のゲート方式は採用しない方針だった。1ファイルに全部書き込む素朴な方式だと、「履歴として何が起きたか」と「今の理解はどうなっているか」が両立しない。

## 決定

event sourcing(追記のみのログ)+ materialized view(そこから導出される現在状態)という定番パターンを採用する。

- **ログ層**: `MemoryEvent`テーブル(`theme`/`extracted_at`/`source_conversation_turn`/`raw_text`)。追記のみ、削除・編集しない。
- **現在状態層**: `memory/<theme-slug>.md`(1テーマ1ファイル)。会話に読み込ませる実体はこちら。対象テーマのログをもとにLLMが書き直す(read-modify-write)。

## 検討した代替案

- 候補→承認ゲート方式(記憶に値する内容をユーザーに都度確認してから保存): 「管理は面倒」という要望に反する。
- 1ファイルへの追記のみ(現在状態層を持たない): テーマが育つにつれ会話に注入するファイルが単調に肥大化し、LLMによる要約・整理が効かなくなる。

## 結果(Consequences)

良い面: チャット履歴と違い、ログ層はLLMが「記憶に値する」と判断したものだけを保持し(フィルタリング)、テーマ単位に束ね直され(再編成)、チャット履歴が将来刈り込まれても無関係に永続する(独立性)。テーマの統合・分割・改名時も、不変なのは`raw_text`のみで`theme`ラベルは機械的に付け替えられるため対応しやすい。`019-diary-domain`がキーを「テーマ」から「日付」に変えて同じ仕組みを再利用する予定であり、パターンとしての再利用性も確認できている。

悪い面: 現在状態ファイルの書き直しをターンごとに毎回行うか、ログ追記は毎ターンでも反映は間引くかは未決定(コストとのバランス、017の未決定事項)。`worth_remembering`の判定自体が無料枠モデルの気まぐれで安定しないことも実機確認済みで、二層構造自体の欠陥ではないがモデル依存の不確実性は残る。
