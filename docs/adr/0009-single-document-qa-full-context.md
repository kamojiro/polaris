# 0009. 単一文書QAは全文インコンテキスト方式を採用する(ベクトル検索を経由しない)

## ステータス

採択

## コンテキスト

`002-papers-ingest-full`でChunk/Embeddingを構築済みで、ライブラリ全体からの横断検索には使える。一方`015-paper-qa-chat`の「この1論文について質問したい」という要件は性質が異なる。研究論文の全文(概ね5,000〜15,000トークン)は、使用中のモデルのコンテキスト長(`qwen3-30b-a3b`: 131K、`qwen3.6-35b-a3b`: 262K)に十分収まる。

## 決定

1論文とのQAはベクトル検索(Chunk/Embedding)を経由せず、`get_paper_full_text`ツールが対象論文の抽出済み全文をそのままエージェントのコンテキストに渡す方式にする。Chunk/Embeddingパイプラインはライブラリ横断検索用として役割を分ける。

## 検討した代替案

- セマンティックチャンキング・目次ベースの階層検索(`016-paper-structured-parsing`寄りの方向性): 方向性としては妥当だが、コンテキストに収まらないほど長いドキュメント向けの技術であり、1論文とのチャットには過剰と判断した。チャンク化・検索特有の精度問題(正しいチャンクを引き当てられるか)を避けられる分、全文をそのまま渡す方が単純かつ正確。

## 結果(Consequences)

良い面: 検索精度の問題(関連チャンクの取りこぼし)が原理的に発生しない。実装もシンプル(`load_full_text()`が`PaperRecord.pdf_path`から都度pypdfで再抽出するだけで、既存Ingest済みデータのスキーマ変更・再Ingestが不要)。会話履歴に一度載った全文はそのまま再利用され、2ターン目以降はtool再呼び出し不要なことを実測確認済み。`013-ir-analysis-domain`もこの方式をそのまま流用している。

悪い面: 毎ターン全文分のトークンが(prompt cachingが安定して効かない限り、ADR-0006参照)再送されるため、長い論文ほどコストが線形に増える(実測: 151k文字の論文で入力58,647トークン)。全文がコンテキスト長を超える極端に長いドキュメントには対応できない(v1はエラー/警告のみ、チャンク化フォールバックは範囲外)。
